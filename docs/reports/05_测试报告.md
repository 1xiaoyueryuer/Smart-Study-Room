## 5. 测试方法：隔离、清库与并发

### 5.1 测试库隔离与守卫

集成测试的启用条件是环境变量 `STUDYROOM_INTEGRATION=true`（`@EnabledIfEnvironmentVariable`，`backend/src/test/java/cn/studyroom/BookingIntegrationTest.java:17`、`FullJourneyIntegrationTest.java:28`）。开启后还有第二道库名守卫：

- 装配层：`@SpringBootTest(properties={"spring.datasource.url=${STUDYROOM_TEST_DB_URL:jdbc:postgresql://127.0.0.1:5433/studyroom_java_test}", ...})`，默认值本身就指向测试库。
- 用例层：`assertTrue(env.getProperty("spring.datasource.url","").endsWith("/studyroom_java_test"),"必须使用独立测试库")`（`BookingIntegrationTest.java:38`），`FullJourneyIntegrationTest.java:41` 直接比对 `current_database()` 是否为 `studyroom_java_test`。
- 清库层：`TestDatabaseCleanup` 在清表前再次比对 `current_database()`，不等即抛 `IllegalStateException("test database only")`（`TestDatabaseCleanup.java:16`）。

库名检查无法区分不同端口上的同名数据库。v1.2 显式把测试连接指向临时 PostgreSQL 和 Redis 实例，执行结束后移除这两个容器。

### 5.2 测试夹具清理

`TestDatabaseCleanup.clear(Store db)`（`TestDatabaseCleanup.java:12—24`）的做法不是删库重建，而是在一个事务里：先 `lockBookings()`，`TRUNCATE complaint_priority_mapping_versions CASCADE`，按依赖顺序删掉 `reviews`、`review_operations` 与关联到申诉/评价的 `notifications`，再 `DELETE FROM` 29 张业务表（含 `reservations`、`usage_records`、`violations`、`complaints`、`appeal_*`、`restrictions`、`notifications`、`audit_events`、`seat_codes`、`rooms`、`users` 等），最后写回一条空的投诉优先级映射版本。事务包裹保证外键与延迟批量的基数约束在整个清理过程中都保持启用，不会因为中间态出现「先删父表再删子表」的失败。这些 SQL 在独立的 `studyroom_java_test` 上执行。

### 5.3 迁移测试用临时 schema

`MigrationIntegrationTest` 不清业务表，而是每次在测试库里建一个随机 schema（`schema="migration_test_"+UUID...`，`MigrationIntegrationTest.java:33`），Flyway 以该 schema 为默认 schema 执行，`cleanDisabled(true)` 防止误 clean，`@AfterEach` 执行 `DROP SCHEMA ... CASCADE`（第 36—38 行）。前置检查是 `SELECT current_database()` 等于 `studyroom_java_test`（第 30—32 行）。因此 128 条迁移用例可以在同一个库里反复跑而不留残渣，也不会碰开发库的 schema 与 flyway 历史。

### 5.4 并发用例如何构造

并发用例通过闩锁或栅栏同步放行请求，检查响应状态及数据库中的最终记录。

- `BookingIntegrationTest.race(n, work)` 用 `Executors.newFixedThreadPool(n)` + `CountDownLatch(1)`，所有线程 `start.await()` 后由主线程 `countDown()` 同时放行，逐个 `future.get(30, TimeUnit.SECONDS)` 收集状态码（第 137—144 行），再断言「200 恰好 1 个、409 恰好 19 个」并核对行数（第 53—59 行）。
- `ComplaintWorkflowIntegrationTest` 用 `CyclicBarrier(3)` 让「到期结算 / 本人查询 / 本人异议」三路同时进入，断言自动关闭事件、通知与审计**各恰好 1 条**。
- `CheckinCorrectionIntegrationTest` 用两路并发补签断言「1 个成功 1 个冲突」，并用同一操作编号的两路并发断言「两次都成功但只有一次真写、使用记录仍 1 条」。
- `RestrictionIntegrationTest`、`ManualViolationIntegrationTest`、`AutomaticRestrictionIntegrationTest`、`SeatCodeIntegrationTest`、`UsageIntegrationTest` 同样用固定线程池 + 闩锁/栅栏并发提交同一操作键或同一事实，断言「只留一条事实、通知与审计各 1 条」。

F12 并发用例模拟六个账号提交同一座位时段，核对只有一笔成功。F13 回滚用例临时添加审计表约束，使批量审计写入失败，再检查座位码表没有残留，最后移除测试约束。

`d0dce50` 新增的 7 个前端测试文件（预约确认摘要、局域网页面加载与轮询、移动端顶栏、记录日期筛选、选座展示、服务端时间与目标时钟、列表分页）随前端全量执行，结果见 6.1。
