## 2. 测试目的与「不是手工点页面」的论证

### 2.1 分层策略

本轮把「能不能用」拆成四层，逐层都有可复跑的入口，而不是靠一个人点几下页面下结论：

| 层 | 对象 | 本层规模 | 失败后果 |
|---|---|---|---|
| 业务断言层 | 后端集成测试（真实 PostgreSQL + Redis） | 589 条 | `mvn package` 失败，打包不出 JAR |
| 单元 / 工程层 | 后端纯单元与工程测试 | 25 条 | 同上 |
| 前端逻辑层 | `frontend/tests/*.test.js`（Node 24 内置 test runner） | 307 条 | 测试进程非零退出 |
| 覆盖率采集层 | JaCoCo 0.8.12 + Node `--experimental-test-coverage` | 只出报告，不设门禁 | 不阻断构建，用于定位未测路径 |

两个技术栈各自独立：后端 **614** 条、前端 **307** 条，两者不合并成一个数字，也不把多次运行相加；后端 614 条本身来自**单次** `mvn -B -ntp package`。

### 2.2 四条可检验的机制（为什么不是「点页面」）

1. **断言是机器判定的，不是人看的。** 每条用例以 `assertEquals` / `assertThrows` / `jsonPath` 判定并写入 surefire 报告；人只负责复核报告，不负责宣判通过。
2. **连的是真实依赖，不是 mock。** 589 条集成测试连接真实 PostgreSQL 17.11 与 Redis 7.2 的独立测试库/库号，走真实 SQL、外键、唯一约束与事务回滚；`ComplaintTransportIntegrationTest` 用的是真嵌入式 Tomcat 的 HTTP 上传下载链路（类注释原文：`真嵌入式Tomcat HTTP；MockMultipart不经过servlet传输限制，不能替代这里。`）。使用替身对象（mock）的只有 `ComplaintFrontendCompatibilityTest`、`StatsSnapshotTest` 这类契约/快照单元测试，它们只占 25 条单元/工程测试的一部分，不被计入 582 条集成测试。
3. **测试库有守卫，跑错库会直接断言失败。** 不清空、不误伤开发库（见第 5 节）。
4. **失败即红。** 本轮若任一条失败，`package` 生命周期即失败、不产出可执行 JAR，不存在「点几下没报错就算过」的中间态。

### 2.3 本轮结果与适用边界

本轮 614 条后端用例中 613 条通过、1 条失败（失败详情与定位见第 8.1 节），构建结果是 BUILD FAILURE；307 条前端用例全部通过。这只说明**自动化测试层面基本可用**：已实现的行为大部分有机器可复跑的验证，并且通过实际执行暴露了一处跨模块回归；不说明需求全部完成、不说明界面可用、不说明真实校园环境可用（见第 9 节）。

## 5. 测试方法：隔离、清库与并发

### 5.1 只连测试库的双重守卫

集成测试的启用条件是环境变量 `STUDYROOM_INTEGRATION=true`（`@EnabledIfEnvironmentVariable`，`backend/src/test/java/cn/studyroom/BookingIntegrationTest.java:17`、`FullJourneyIntegrationTest.java:28`）。开启后还有第二道库名守卫：

- 装配层：`@SpringBootTest(properties={"spring.datasource.url=${STUDYROOM_TEST_DB_URL:jdbc:postgresql://127.0.0.1:5433/studyroom_java_test}", ...})`，默认值本身就指向测试库。
- 用例层：`assertTrue(env.getProperty("spring.datasource.url","").endsWith("/studyroom_java_test"),"必须使用独立测试库")`（`BookingIntegrationTest.java:38`），`FullJourneyIntegrationTest.java:41` 直接比对 `current_database()` 是否为 `studyroom_java_test`。
- 清库层：`TestDatabaseCleanup` 在清表前再次比对 `current_database()`，不等即抛 `IllegalStateException("test database only")`（`TestDatabaseCleanup.java:16`）。

三层守卫只校验**库名**、不校验端口，因此换一个端口起同名测试库并行跑时不需要改任何测试文件。

### 5.2 清库只清测试库，不动开发库

`TestDatabaseCleanup.clear(Store db)`（`TestDatabaseCleanup.java:12—24`）的做法不是删库重建，而是在一个事务里：先 `lockBookings()`，`TRUNCATE complaint_priority_mapping_versions CASCADE`，按依赖顺序删掉 `reviews`、`review_operations` 与关联到申诉/评价的 `notifications`，再 `DELETE FROM` 29 张业务表（含 `reservations`、`usage_records`、`violations`、`complaints`、`appeal_*`、`restrictions`、`notifications`、`audit_events`、`seat_codes`、`rooms`、`users` 等），最后写回一条空的投诉优先级映射版本。事务包裹保证外键与延迟批量的基数约束在整个清理过程中都保持启用，不会因为中间态出现「先删父表再删子表」的失败。开发库 `studyroom_java` 从不在这些 SQL 的范围内，本轮全程未操作。

### 5.3 迁移测试用临时 schema

`MigrationIntegrationTest` 不清业务表，而是每次在测试库里建一个随机 schema（`schema="migration_test_"+UUID...`，`MigrationIntegrationTest.java:33`），Flyway 以该 schema 为默认 schema 执行，`cleanDisabled(true)` 防止误 clean，`@AfterEach` 执行 `DROP SCHEMA ... CASCADE`（第 36—38 行）。前置检查是 `SELECT current_database()` 等于 `studyroom_java_test`（第 30—32 行）。因此 127 条迁移用例可以在同一个库里反复跑而不留残渣，也不会碰开发库的 schema 与 flyway 历史。

### 5.4 并发用例如何构造

并发不是「先后调用两次」，而是同一时刻放行：

- `BookingIntegrationTest.race(n, work)` 用 `Executors.newFixedThreadPool(n)` + `CountDownLatch(1)`，所有线程 `start.await()` 后由主线程 `countDown()` 同时放行，逐个 `future.get(30, TimeUnit.SECONDS)` 收集状态码（第 137—144 行），再断言「200 恰好 1 个、409 恰好 19 个」并核对行数（第 53—59 行）。
- `ComplaintWorkflowIntegrationTest` 用 `CyclicBarrier(3)` 让「到期结算 / 本人查询 / 本人异议」三路同时进入，断言自动关闭事件、通知与审计**各恰好 1 条**。
- `CheckinCorrectionIntegrationTest` 用两路并发补签断言「1 个成功 1 个冲突」，并用同一操作编号的两路并发断言「两次都成功但只有一次真写、使用记录仍 1 条」。
- `RestrictionIntegrationTest`、`ManualViolationIntegrationTest`、`AutomaticRestrictionIntegrationTest`、`SeatCodeIntegrationTest`、`UsageIntegrationTest` 同样用固定线程池 + 闩锁/栅栏并发提交同一操作键或同一事实，断言「只留一条事实、通知与审计各 1 条」。

这类用例是有意义的：它们验证的是唯一约束、行锁与幂等键在真实数据库上确实生效，而不是在单线程里「看起来没报错」。

## 11. 注解：术语与缩略语

| 术语 | 含义 |
|---|---|
| 集成测试 | 启动真实 Spring 上下文、连接真实 PostgreSQL/Redis 执行断言的测试，本文指 589 条 |
| 单元 / 工程测试 | 不连数据库的纯逻辑或工程行为测试，本文指 25 条 |
| 守卫 | 测试类前置的启用条件与库名校验，防止测试在错误环境或错误库上运行 |
| 测试库 / 开发库 | `studyroom_java_test`（可被测试清理）/ `studyroom_java`（本轮全程未操作） |
| 夹具（fixture） | 测试中构造的模拟用户、空间、座位与历史数据，不是校园真实数据 |
| 注入时钟 | 由测试指定当前时间的 `Clock`，用于验证 15 分钟、7 天、168 小时等规则，不等同真实等待 |
| 覆盖率口径 | 指令 = 字节码指令被执行比例；分支 = 判断分支被走到比例；行 = 源码行被执行比例 |
| JaCoCo | Java 覆盖率采集工具，本项目只采集不设门禁，覆盖率低不会使构建失败 |
| V 编号 | 项目唯一的问题编号，统一维护在 02 报告 A.7，本报告只引用不复述 |
| PV / SC | 原型走查与场景走查编号，属人工材料，与本文自动化结论互不替代 |
| surefire | Maven 的测试执行插件，其报告是本报告条数与结果的直接来源 |
